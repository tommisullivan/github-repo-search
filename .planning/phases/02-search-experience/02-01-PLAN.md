<objective>
Establish the App Router boundaries the whole search experience renders through: the root layout in Japanese, a Japanese `loading.tsx` for the server render, and a Japanese `error.tsx` that catches the thrown `GitHubRequestError` the Phase 1 client uses for transport faults and 5xx responses.

Purpose: these three files decide what a user sees when data is *not* available. They must exist before the search page in plan 02-02, because that page is written to rely on them (D-07: the page does not `try`/`catch` the client, so `error.tsx` is the only place a `NETWORK` failure can surface).

Output: `layout.tsx` updated to `lang="ja"` with Japanese metadata, new `loading.tsx` and `error.tsx` in `src/app/`, and colocated tests for both boundaries.
</objective>

App Router contract (Next.js 16 App Router):
- `src/app/loading.tsx` exports default a Server Component; rendered by the router during a server render.
- `src/app/error.tsx` exports default a Client Component (`"use client"` is required); receives `{ error: Error & { digest?: string }, reset: () => void }`.
</interfaces>

<boundary_rules>
- `error.tsx` must be a Client Component. This is a framework requirement, not a policy choice — an error boundary cannot be a Server Component in the App Router.
- Neither boundary may render `error.message`, `error.stack`, or `error.digest`. AGENTS.md forbids rendering a raw error object or stack trace to the user; every user-facing string is a fixed Japanese literal.
- Neither boundary may import from `src/lib/github/` — they render UI only. The `error.tsx` prop type is Next's, not Phase 1's `GitHubRequestError`, so no boundary lint rule is violated.
- No `dangerouslySetInnerHTML` (SEC-03; the ESLint rule from `src/eslint-rules.test.ts` will fail the build otherwise).
</boundary_rules>
</context>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Server error object → error boundary props | Anything thrown by `searchRepositories` or `githubFetch` reaches `error.tsx` as an `Error`; its `message` is English operator-facing text that must not become user-facing |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Information disclosure | `error.tsx` rendering `error.message` | mitigate | The boundary renders only fixed Japanese literals. Asserted in a test that supplies a distinctive marker string as `error.message` and confirms it is absent from the document (D-13 forbids raw error rendering; AGENTS.md forbids stack traces and error objects reaching the user) |
| T-02-02 | Denial of service | An `error.tsx` that itself throws | accept | The boundary uses no runtime data — every string is a literal, `reset` is a function call. There is no code path that can throw at render |
| T-02-SC | Tampering | npm installs | mitigate | This plan installs nothing. A diff to `package.json` or `package-lock.json` is a plan violation |
</threat_model>
