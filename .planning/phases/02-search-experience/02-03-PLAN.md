<boundary_rules>
- `SearchInput.tsx` **is** a Client Component (`"use client"` on line 1) — it uses `useState`/`useEffect`/`useRouter`, which require the client. This is the exception to the "Server Components by default" rule that AGENTS.md explicitly permits, and it is pushed as far down the tree as possible (the input alone is client; the page and the results stay on the server).
- `Pagination.tsx` is a **Server Component** — its output is a pair of `<Link>` elements that only need to know the current page and `hasNextPage`. No `"use client"`.
- `SearchInput.tsx` **must not** import from `@/lib/github/`. The boundary lint rule in `src/eslint-rules.test.ts` fires against exactly this pattern — a token-leak vector into the client bundle.
- **No `use-debounce`, no `lodash`, no `lodash.debounce`, no `debounce` package.** D-15 and D-16 forbid a debounce dependency. If Task 1 finds it needs one, that is a signal to stop and raise the decision, not to install.
- **`router.replace`, never `router.push`, on keystroke or page change** (D-03). A `router.push` on debounce fires would fill browser history with one URL per debounced keystroke — the back button would traverse them one at a time.
- No `window.location`, no `history.pushState` — the router is the only mechanism.
</boundary_rules>

  <files>src/components/SearchInput.tsx, src/components/SearchInput.test.tsx</files>
  <behavior>
    - `SearchInput` accepts `{ initialQuery: string; debounceMs?: number }`. `debounceMs` defaults to 300 (D-17); a test can override it to 0 to synchronise assertions.
    - The rendered element is an `<input type="search">` with a Japanese `aria-label` (e.g. "リポジトリを検索") and a Japanese `placeholder` (e.g. "キーワードを入力"). It is wrapped in a `<label>` or associated with one via `htmlFor` so the label-input relationship is programmatic, not visual only.
    - The input's initial value is `initialQuery`.
    - As the user types, `router.replace()` is called with `/?q=<current value>&page=1` **at most once per debounce window**. Typing four characters in a burst of ≤ debounceMs → **one** `router.replace` call, not four.
    - Whitespace-only input calls `router.replace("/")` (empty query removes the parameter, giving a clean canonical URL). A cleared field returns to the same clean URL.
    - Every keystroke resets `page` to `1` — a new keyword should never leave the user on page 5 of the previous search.
    - The debounce uses `useDeferredValue` + `useEffect` **or** a custom `useDebounce(value, delay)` hook backed by `setTimeout`/`clearTimeout`. No import from `use-debounce`, `lodash`, or any other npm package for the debounce.
    - The component is a Client Component (`"use client"` on line 1).
  </behavior>
  <action>
Create `src/components/SearchInput.tsx` with `"use client"` on line 1.

Choose the debounce approach and put a comment naming the choice and its rationale directly above the debounce code:
- **Option A: React 19 `useDeferredValue` + `useEffect`.** `useDeferredValue(query)` yields a debounced-by-render value; an effect runs `router.replace` when the deferred value changes. Simpler, but the delay is React-scheduled, not fixed to 300ms.
- **Option B: A tiny `useDebounce(value, delay)` hook.** `useEffect` with `setTimeout` writes `value` into an internal state after `delay`; the cleanup calls `clearTimeout`. Fixed delay; easier to test with a controlled `delay` prop.

**Recommendation: Option B.** The test needs a deterministic delay so it can drive `vi.useFakeTimers()` and advance time by a known amount; `useDeferredValue`'s scheduler-driven timing is not directly controllable from a test. The `debounceMs` prop is what makes Option B testable — a comment in the file states this.

Implementation shape:
```
// pseudo-code, not the final file
const [query, setQuery] = useState(initialQuery);
const debouncedQuery = useDebounce(query, debounceMs);
const router = useRouter();

useEffect(() => {
  const trimmed = debouncedQuery.trim();
  const target = trimmed === ""
    ? "/"
    : `/?q=${encodeURIComponent(trimmed)}&page=1`;
  router.replace(target);
}, [debouncedQuery, router]);
```

- Skip the initial-mount `router.replace` when `debouncedQuery === initialQuery` (avoid an unnecessary URL rewrite on first render that would trigger a re-render loop or a lint warning). Guard with a `useRef` for "first render" or by comparing to `initialQuery` inside the effect.
- `router.replace`, not `router.push` — the comment explains why (D-03: keystroke-per-history-entry is a UX bug).
- `encodeURIComponent` on the keyword — `q` containing `&` or `=` cannot introduce a second parameter (SEC-03).
- `useDebounce` lives at the bottom of this file as a small local hook, not in a separate file — one hook, one caller, colocating is right.

Create `src/components/SearchInput.test.tsx`. Use `vi.useFakeTimers()` and `vi.useRealTimers()` in `beforeEach`/`afterEach`. Mock `next/navigation`'s `useRouter` to return `{ replace: vi.fn() }`.

Tests:

2. **Debounces** — user types "abc" (one letter at a time), then `vi.advanceTimersByTime(300)`. Asserts `router.replace` was called exactly **once** with `/?q=abc&page=1`. This is SRCH-05's positive assertion.
3. **Debounces across a burst** — user types "a", advances 100ms, types "b", advances 100ms, types "c", advances 300ms. Asserts `router.replace` was called **once** with `/?q=abc&page=1` — the intermediate timers were reset.
4. **Whitespace-only** — user types "   " and advances timers. Asserts `router.replace` was called with `/` (canonical empty URL), not `/?q=%20%20%20&page=1`.
5. **Page reset** — set `initialQuery="react"`, then user types "vue" and advances timers. Asserts `router.replace` was called with `/?q=vue&page=1` — even though the current URL might be on `page=5`, a new keyword resets to 1.

    - Otherwise, both links are `<Link href="/?q=...&page=N±1">` with the keyword preserved and the page number changed.

  <action>
Create `src/components/Pagination.tsx` — a Server Component. Import `Link` from `next/link`.

Build the previous and next hrefs once at the top of the function: `` const prevHref = `/?q=${encodeURIComponent(q)}&page=${page - 1}` ``, same for `next`. Determine `isPrevDisabled = page <= 1` and `isNextDisabled = !hasNextPage`.

Render pattern (name-only, not the final markup):
```
<nav aria-label="...">
  {isPrevDisabled
    ? <span aria-disabled="true" role="link">前へ</span>
    : <Link href={prevHref} rel="prev">前へ</Link>}
  <span aria-live="polite">{page} ページ目</span>
  {isNextDisabled
    ? <span aria-disabled="true" role="link">次へ</span>
    : <Link href={nextHref} rel="next">次へ</Link>}
</nav>
```

The `role="link"` on the disabled span keeps the semantics consistent between disabled and enabled states — a screen reader hears "link" for both, plus "disabled" for the inactive one. Rationale in a comment (D-19: stable tab order and reading order across pages).

3. **Last reachable page** — `page=50, hasNextPage=false`. Asserts `次へ` has `aria-disabled="true"`, `前へ` is an active link with `page=49`.

| Threat ID | Category | Component | Disposition | Mitigation Plan |
