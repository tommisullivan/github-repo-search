  <name>Task 1: Search unit — query guard, encoding, pagination, and the 1000-result ceiling</name>
  <files>src/lib/github/search.ts, src/lib/github/search.test.ts</files>
  <behavior>
    - A 200 search payload maps to `{ ok: true, data }` where each item carries `stars` from `stargazers_count`, `forks` from `forks_count`, `openIssues` from `open_issues_count`, and `owner.avatarUrl` from `owner.avatar_url`.
    - `""`, `"   "`, and `"\n\t"` each return `{ ok: false, error: { code: "INVALID_QUERY" } }` and `fetch` was **not** called (API-04 — GitHub's 422 never occurs because no request is made).
    - The request URL carries `per_page=20` (D-12) and the requested `page`.
    - A query containing spaces, `&`, `=`, `#`, and Japanese characters produces exactly one `q` parameter whose decoded value equals the trimmed input — verified by parsing the outgoing URL with `URL`/`URLSearchParams`, not by string matching.
    - A query of `next&per_page=100` cannot alter `per_page`: the parsed outgoing URL still has `per_page` equal to `20` and exactly one `q`.
    - A 200 payload with `total_count: 0` and `items: []` returns `{ ok: true, data }` with `totalCount: 0` and `items: []` — a success, not a failure. It must be impossible for a caller to confuse this with a rate limit.
    - A 403 rate-limit response propagates as `{ ok: false, error: { code: "RATE_LIMIT", resetAt } }` unchanged.
    - A 422 from GitHub propagates as `{ ok: false, error: { code: "INVALID_QUERY" } }`.
    - A 500 from GitHub does **not** become a returned failure. `githubFetch` throws `GitHubRequestError`, this unit does not catch it, and the rejection reaches the caller — asserted with `await expect(searchRepositories("react")).rejects.toBeInstanceOf(GitHubRequestError)`. The unit's contract is therefore *returns a `Result`* **and** *may throw*, and Phase 2 must handle both (D-03, D-05a).
    - A transport fault (a `fetch` that rejects with `TypeError`, twice) also rejects rather than returning, for the same reason and with the same assertion.
    - `page` of `0`, `-3`, `1.5`, and `NaN` normalise to `1`.
    - `page` of `51` or higher returns `INVALID_QUERY` without calling `fetch` — page 51 begins at result 1001 and is past GitHub's ceiling, so the request could only ever 422.
    - `hasNextPage` is `true` when more results remain within the ceiling and `false` on the last reachable page, including when `total_count` exceeds 1000 but the current page is the 50th.
    - The `revalidate` passed to `githubFetch` is `60` (D-09).
  </behavior>
  <action>
Create `src/lib/github/search.ts` — the search capability unit. Open with a comment stating it is server-side only.

Export `SEARCH_PER_PAGE = 20` (D-12: substantial without endless scrolling, small payload, and it exercises pagination naturally inside the ceiling — GitHub's own default of 30 buys nothing here) and `SEARCH_MAX_RESULTS = 1000` (GitHub's hard cap on search results), and derive the maximum page from them rather than writing `50` anywhere.

`searchRepositories(query: string, page = 1)`:

Guard first, before anything else. Trim the query; if the result is empty, return `{ ok: false, error: { code: "INVALID_QUERY" } }` immediately. This is API-04 and it is a guard, not an optimisation: the point is that GitHub never sees the request at all. Normalise `page` next — anything that is not a positive integer becomes `1`; anything past the derived maximum page returns `INVALID_QUERY` without a request, for the same reason.

Build the query string with `URLSearchParams` only (SEC-03, SECURITY.md attack-surface row one). Never concatenate, never template-interpolate a user value into the path. Set `q` to the trimmed query, `per_page` to `SEARCH_PER_PAGE`, and `page` to the normalised page. Compose the path as `/search/repositories?` followed by the serialised params.

Call `githubFetch<GitHubSearchPayload>` with that path, `endpoint: "search/repositories"`, and `revalidate: 60`. The `cache` option is deliberately **not** this unit's business — `githubFetch` owns the opt-in that API-05 depends on, and passing it from here would put the same decision in two places. On a failure result, return it unchanged — the unit adds no interpretation and no prose (D-05, D-06). Do **not** wrap the call in `try`/`catch`: a `GitHubRequestError` thrown by `githubFetch` must propagate through this unit untouched, because D-03 routes it to `error.tsx`, and catching it here would silently convert an unexpected fault into a state the UI has no branch for.

On success, map the payload to `SearchResult`: `items` mapped through a small local `toRepoSummary(payload: GitHubRepoSummaryPayload): RepoSummary` helper, `totalCount` as GitHub's raw `total_count` (D-14 — Phase 2 renders the real number), `page`, `perPage`, and `hasNextPage` computed as the current page's last index being below `Math.min(total_count, SEARCH_MAX_RESULTS)`. Keep `toRepoSummary` unexported unless `repo.ts` genuinely needs it — it must not become a cross-unit import; if both need it, that is a signal to move it into `@/types/github` as a mapping helper rather than to import across the boundary.

Write `src/lib/github/search.test.ts` with one named test per `<behavior>` bullet, mocking at the `fetch` boundary per TESTING.md. Two assertions are the ones that must not be skipped, so write them deliberately: the guard tests must assert `fetch` was never called (not merely that the result is `INVALID_QUERY`), and the empty-result test must assert the result is `ok: true` — a rate limit rendering as "no results" is the single most misleading failure this app can produce, and this is the layer where they become indistinguishable if the types are wrong.
  </action>

  <behavior>

    - Given a payload with `subscribers_count: 7` and `watchers_count: 4321` and `stargazers_count: 4321`, the result has `watchers === 7` and `stars === 4321`. The test is named so a reviewer reading the CI log sees the trap being guarded.

    - A blank or whitespace-only `owner` or `repo` returns `{ ok: false, error: { code: "NOT_FOUND" } }` and `fetch` was not called.
    - A 404 returns `{ ok: false, error: { code: "NOT_FOUND" } }` — returned, not thrown, so Phase 3's page can call `notFound()` itself (D-01).
    - A 403 rate-limit response propagates as `RATE_LIMIT` with `resetAt`.
    - A 500 from GitHub propagates as a thrown `GitHubRequestError` — this unit does not catch it — asserted with `await expect(getRepository("facebook", "react")).rejects.toBeInstanceOf(GitHubRequestError)`. Both units return a `Result` **and** may throw; that dual contract is what Phase 3 is written against (D-03, D-05a).
    - The `revalidate` passed to `githubFetch` is `300` (D-09).
  </behavior>
  <action>
Create `src/lib/github/repo.ts` — the repository capability unit. Open with a comment stating it is server-side only.

`getRepository(owner: string, repo: string)`:

Guard first: trim both arguments; if either is empty, return `{ ok: false, error: { code: "NOT_FOUND" } }` without a request. `NOT_FOUND` rather than `INVALID_QUERY` is the honest code — a blank owner names no repository, and Phase 3 renders the not-found page, which is what a user in that situation should see.

Build the path with `encodeURIComponent` on each segment separately (SEC-03, SECURITY.md attack-surface row two): a crafted value must not be able to escape its segment and address a different endpoint. Encode per segment, never encode the whole path at once, and never template a raw argument into the string.

Call `githubFetch<GitHubRepoDetailPayload>` with `endpoint: "repos/{owner}/{repo}"` and `revalidate: 300` (D-09: detail changes slowly and is the page most likely to be reloaded during review; search gets 60 because results shift as repositories are created and starred — one number would be wrong for one of them).

On a failure result, return it unchanged, and do not `try`/`catch` around `githubFetch` — a thrown `GitHubRequestError` must propagate to `error.tsx` (D-03). On success, map to `RepoDetail` and set `watchers` from `subscribers_count`. Put the explanation at the mapping line, not in a header comment, because the mapping line is where a reader will question it: REST `watchers_count` is a duplicate of `stargazers_count`, so using it would render the star count twice under two labels and read as a bug; `subscribers_count` is the real watcher count and exists only on this endpoint. This mapping is the single place in the codebase that knows about the quirk — nothing else needs to.

Write `src/lib/github/repo.test.ts` with one named test per `<behavior>` bullet, mocked at the `fetch` boundary. Name the watchers test so it reads as the guard it is, for example "maps watchers from subscribers_count, not from the watchers_count duplicate of stars". Give the path-encoding tests fixture values that would genuinely traverse if unencoded, and assert against the parsed `URL` object rather than a substring match — a substring assertion can pass on a URL that is still wrong.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User keyword → GitHub query string | Free text from a URL query parameter is sent upstream |
| Route params `owner` / `repo` → GitHub URL path | User-controlled path segments decide which resource is addressed |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-12 | Tampering | `search.ts` query construction | mitigate | `q` is set through `URLSearchParams` only, so an injected `&per_page=100` or `&q=` becomes part of the value rather than a new parameter. Asserted by parsing the outgoing URL and checking there is exactly one `q` and `per_page` is still 20 (SEC-03) |
| T-01-13 | Tampering | `repo.ts` path construction | mitigate | Each segment passes through `encodeURIComponent` separately, so `../../search` cannot escape `/repos/`. Asserted against the parsed `pathname`, not a substring (SEC-03) |
| T-01-14 | Denial of service | Unbounded pagination requests | mitigate | Pages past GitHub's 1000-result ceiling are refused locally, so an attacker walking `?page=99999` burns no upstream quota |
| T-01-15 | Denial of service | Blank-query request storm | mitigate | Blank and whitespace-only queries return before any request, so the cheapest possible abusive input costs zero quota (API-04) |
| T-01-16 | Information disclosure | Search keywords in logs | accept | Keywords are public search terms with no identity attached; recorded and justified in OPERATIONS.md. Revisit only if the app ever gains accounts |
| T-01-17 | Elevation of privilege | Cross-unit import breaking the boundary | mitigate | Neither unit imports the other; checked by grep in this plan's verification and again in plan 01-04's sweep |
| T-01-SC | Tampering | npm installs | mitigate | This plan installs nothing. A diff to `package.json` or `package-lock.json` is a plan violation — stop for human review |
</threat_model>
