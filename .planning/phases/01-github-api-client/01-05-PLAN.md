Three specific statements are known to be wrong after this phase. Find them precisely rather than rewriting the documents wholesale — these are good documents and a broad rewrite would lose reasoning that is still correct.

1. `docs/ARCHITECTURE.md` — the "Typed errors, distinct UI" section, and both Mermaid sequence diagrams, show `RateLimitError` / `ValidationError` / `NotFoundError` / `NetworkError` classes being **thrown** up to `error.tsx`. The phase implements the hybrid model (D-01..D-04): rate limit, not found, and invalid query are **returned** as a `Result` failure; only transport faults and unrecognised statuses throw.
2. `docs/OPERATIONS.md` — the observability table names `pino` as the default logging mechanism. The phase uses `console.log` with `JSON.stringify` and no dependency (D-17, D-18).
3. `docs/TESTING.md` — the mocking example asserts `rejects.toBeInstanceOf(RateLimitError)`, and the "Unit — the GitHub client" section and failure-mode table describe the thrown-class model. All three describe a contract that no longer exists.

  <action>
Make three targeted corrections. In each case give the reasoning, not just the new fact — these documents earn their place by explaining why, and a reviewer reading them is assessing judgement.

**`docs/ARCHITECTURE.md`.** Replace the "Typed errors, distinct UI" section's table with the implemented vocabulary: the returned failure codes `RATE_LIMIT` (carrying `resetAt`), `NOT_FOUND`, and `INVALID_QUERY`, and the thrown `GitHubRequestError` carrying `NETWORK` for transport faults and unrecognised statuses. State plainly why the split exists, which is the strongest single decision in this phase: in production Next sanitises server errors before the client error boundary receives them, so branching on error type inside `error.tsx` is unreliable — per-state UI would work in development and silently degrade to a generic message after deployment, which is a bug class that only appears in production. Note that `NETWORK` is the one case where no branching is needed, because the generic retry message in `error.tsx` is the correct and complete answer for it.

Update both Mermaid sequence diagrams so the rate-limit, 422, and 404 arrows return a typed result to the page rather than throwing, and so the detail 404 path shows the page calling `notFound()` itself. Keep the transport-failure arrow throwing to `error.tsx`.

Update the directory-layout listing so the `src/lib/github/` and `src/types/github.ts` rows read **Built** rather than **Planned · P1**, and add `log.ts` to it. Update the build-status prose at the top of the document accordingly, and change any node classed as `planned` in the Mermaid diagrams that is now built.

**`docs/OPERATIONS.md`.** Change the logging row of the observability table from `pino` to `console.log` with `JSON.stringify`, and record the reason: AGENTS.md requires preferring the platform over a library, a read-only app with one upstream needs no levels, transports, or redaction machinery, and Next already writes stdout — so the dependency would buy nothing (D-17, D-18). In the "Unit — the GitHub client" section, replace the list of error class names with the returned-code vocabulary plus the thrown `GitHubRequestError`, and keep the sentence about the whitespace-only query being rejected before a request, which is still exactly right.
