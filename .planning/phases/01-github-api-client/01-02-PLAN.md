<objective>
Settle by measurement the one thing Phase 1 cannot assume: whether Next 16 actually caches a repeated GitHub read in this project's configuration, and under which fetch options.

This plan exists because the assumption is load-bearing and was already wrong once. D-11a records the correction: `fetch` is **not** cached by default in Next 15+, so caching must be opted into explicitly with `cache: 'force-cache'` alongside `next: { revalidate }`. An app that passes `revalidate` alone would burn quota on every render, pass every test in CI, and only reveal itself as rate-limit errors under real use. D-11b records the second open question: passing an `AbortSignal` — which OBS-02's timeout needs — documentably opts a request out of *memoization*, and the docs do not say whether it also opts out of the *data cache*.

API-05 and OBS-02 can therefore collide, and no amount of reading settles it. This plan counts requests.

Purpose: plan 01-03 writes `githubFetch` exactly once. It should write it against a measured answer rather than discovering the truth in production. This is why the spike is Wave 1 and depends on nothing — it can invalidate the client's whole design, so it must not run after the client is built.

Output: a dated, version-stamped findings subsection in `docs/OPERATIONS.md` carrying the four-cell matrix and the decision plan 01-03 implements, plus a human sign-off on that decision.
</objective>

  <name>Task 1: Build the counting harness and measure the four-cell matrix</name>
  <files>docs/OPERATIONS.md</files>
  <action>
Do **not** call `api.github.com`. Build a local counting server so the result is deterministic, free, and repeatable, and so the answer does not depend on GitHub's own cache headers.

**Harness — all of it temporary, none of it committed.** Write both pieces into the scratch directory, not the repository, except the probe route which must live under `src/app/` to be a real route.

1. A throwaway Node HTTP server (plain `node`, no dependencies) listening on `127.0.0.1:4599`, serving four independent paths `/probe/a`, `/probe/b`, `/probe/c`, `/probe/d`, each with its own request counter. Four paths rather than one because the fetch cache is keyed on the URL, and one shared path would let one cell's cached entry answer another cell's request — which would look exactly like caching that is not there. Each response returns `content-type: application/json`, a body of `{"cell":"<c>","serverCount":<n>}`, and headers `x-ratelimit-limit: 60`, `x-ratelimit-remaining: <60 - n>`, `x-ratelimit-reset: <a fixed future Unix second>`. The decreasing `remaining` and the embedded `serverCount` are the whole mechanism: a cache hit renders a stale number while the server's own counter does not advance, so staleness is visible in the rendered HTML and countable at the server independently.

2. A temporary route at `src/app/cache-probe/page.tsx` — a Server Component that awaits `searchParams`, reads a `cell` parameter, and calls the matching probe path. Reading `searchParams` is deliberate: it makes the route dynamic, exactly as the real search page will be, so the measurement is of the data cache and not of build-time prerendering. Render the returned `serverCount` and the `x-ratelimit-remaining` header value as text.

**The matrix. Four cells, and all four are required** — a two-cell run is what produced the wrong answer the first time.

| Cell | Path | `fetch` options |
|---|---|---|
| a | `/probe/a` | `{ next: { revalidate: 60 } }` |
| b | `/probe/b` | `{ next: { revalidate: 60 }, signal: AbortSignal.timeout(5000) }` |
| c | `/probe/c` | `{ cache: "force-cache", next: { revalidate: 60 } }` |
| d | `/probe/d` | `{ cache: "force-cache", next: { revalidate: 60 }, signal: AbortSignal.timeout(5000) }` |

Cell **a** is the configuration the plans originally specified and D-11a says does not cache. Cell **c** is what D-11a says is required. Cell **d** is the one that decides whether OBS-02's timeout and API-05's cache can coexist. Cell **b** exists so that if a and b differ, the signal's effect is separable from the `cache` option's.

**Running it, in this order, because each step removes a known confound:**

1. Start the probe server.
2. `npm run build`. Read the route table it prints and record whether `/cache-probe` is listed as dynamic (`ƒ`) or static (`○`). If it is static the measurement is invalid — the `searchParams` read is not doing its job and must be fixed before continuing.
3. **Restart the probe server** so all four counters are zero. The build may have issued requests during prerendering; a counter that starts non-zero silently shifts every conclusion by one.
4. `npx next start --port 3100`. Production build only — dev mode has an HMR fetch cache that would confound the result, per the Troubleshooting section of the fetch doc.
5. Drive it with `curl`, three times per cell, same URL each time: `for cell in a b c d; do for i in 1 2 3; do curl -s "http://127.0.0.1:3100/cache-probe?cell=$cell"; done; done`. `curl` and not a browser, because a browser hard refresh sends `cache-control: no-cache`, which the docs say makes `options.cache` and `options.next.*` ignored entirely.
6. Read the four server counters.

**Reading the result.** Per cell, a final count of **1** against 3 requests means it cached; **3** means it did not. Anything else (2) means something is non-deterministic — say so rather than rounding it to a conclusion, and re-run before drawing one.

From the four counts, answer three questions explicitly:

- **Q1 — does `next: { revalidate: 60 }` alone cache?** Cell a. If it does not, D-11a is confirmed and the plans that specified it were wrong.
- **Q2 — does `cache: 'force-cache'` change the answer?** Cell c against cell a. This is the question that decides what `githubFetch` ships.
- **Q3 — does an AbortSignal opt the request out of the data cache?** Cell d against cell c, and cell b against cell a. The docs state a signal opts out of memoization; whether it also opts out of the persistent data cache is not stated anywhere and is the reason this plan exists.

Then answer a fourth from the rendered output rather than the counts:

- **Q4 — what do the rate-limit headers say on a cache hit?** On any cell that demonstrably cached, check whether the rendered `x-ratelimit-remaining` is the stale value from the first call. If it is, a headroom figure taken from a cached response is historical, and the log line in plan 01-03 must not present it as current.

Record the raw counts, the rendered values, and the exact commands run. Keep the harness in place — Task 2 records it and plan 01-03 recreates it to confirm the shipped client end to end.

**Carry the finding forward as one of these three outcomes.** Which one applies is decided by the counts, not by preference:

- **Cell c cached but cell d did not.** The signal disables the data cache, so the two requirements are in tension. `githubFetch` ships `{ cache: "force-cache", next: { revalidate } }` with **no** signal, and enforces the deadline with `Promise.race` against a timer that rejects with `new DOMException("...", "TimeoutError")` so `toRequestError` still classifies it as a timeout. Record the trade-off honestly rather than quietly: the render stops waiting, but the underlying request is no longer cancelled. Then fix the two rows of the resilience table this makes untrue — **Cancellation** ("Propagate the request's abort signal") and **Timeout** ("via `AbortSignal.timeout()`") — so the document describes what the code does. A resilience table describing a mechanism the code does not use is worse than an empty cell.
- **Neither c nor d cached.** Do **not** quietly drop API-05, and do not "simplify" it to an uncached client. Record the finding, state what caching would require in this configuration (route segment `revalidate`, `unstable_cache`, or `cacheComponents`), and escalate at Task 3. A phase requirement being contradicted by the framework is the user's decision, not the executor's workaround.
