<decision_reconciliation>
CONTEXT.md D-02 and D-03 are in tension with D-05 about where `NETWORK` lives. D-02/D-03 say transport faults are **thrown**; D-05 lists `NETWORK` among the codes the client speaks. Both are honoured as follows, and this reconciliation is binding for the whole phase:

- `GitHubErrorCode` is exactly the four codes from D-05 — it is the phase's one error vocabulary.
- The **returned** `Result` failure can only be `RATE_LIMIT`, `NOT_FOUND`, or `INVALID_QUERY`. These are the states where the UI must render something specific, and per D-04 they cannot be branched on inside `error.tsx` in production.
- `NETWORK` is the code carried by the **thrown** `GitHubRequestError`. It covers transport faults and unrecognised HTTP statuses — the two cases where the UI has no specific action to offer and `error.tsx`'s generic retry message is the correct and only answer. No production branching is required for it, so D-04's failure mode does not apply.
</decision_reconciliation>

<task type="auto" tdd="true">
  <name>Task 2: Define the failure vocabulary, Result type, and status mapping</name>
  <files>src/lib/github/errors.ts, src/lib/github/errors.test.ts</files>
  <behavior>
    - A 403 response whose `x-ratelimit-remaining` is `"0"` maps to `{ code: "RATE_LIMIT", resetAt }` where `resetAt` is the integer from `x-ratelimit-reset`.
    - A 429 response maps to `RATE_LIMIT` the same way.
    - When `retry-after` is present it wins over `x-ratelimit-reset`, and `resetAt` becomes now-in-seconds plus that many seconds (OPERATIONS.md calls `retry-after` authoritative when present).
    - When neither header is usable, `resetAt` falls back to now-in-seconds plus 60, so the UI always has a number to render.
    - A 403 that is *not* rate-limit exhaustion (no `retry-after`, and `x-ratelimit-remaining` absent or non-zero) maps to `null` — the caller throws.
    - 404 maps to `{ code: "NOT_FOUND" }`; 422 maps to `{ code: "INVALID_QUERY" }`.
    - 500, 502, and any other non-ok status map to `null`.
    - `toRequestError` on a `TypeError` returns a `GitHubRequestError` with `code === "NETWORK"`, `status === undefined`, and the original error preserved as `cause`.
    - `toRequestError` on a `DOMException` named `TimeoutError` returns a `GitHubRequestError` whose message identifies it as a timeout.
    - `toRequestError(cause, 500)` returns an error with `status === 500`.
    - No `GitHubRequestError` message or property contains a token value.
  </behavior>
  <action>
Create `src/lib/github/errors.ts` implementing exactly the interface block in `<context>`. This module is the shared error core from the ARCHITECTURE.md boundary table: it may import from `@/types/github` and nothing else, and it must never import `client.ts`, `search.ts`, or `repo.ts`.

`GitHubErrorCode` is the four-code union from D-05 and is the only error vocabulary in the phase — no other string literals describing failure may be introduced anywhere in `src/lib/github/`. Per D-05 and D-06 the module contains **no user-facing prose**; Japanese copy is Phase 2's job. Error `message` strings are English operator-facing text only and are never rendered.

`GitHubFailure` is the discriminated union of the three *returned* codes. `RATE_LIMIT` carries `resetAt: number` (Unix seconds) per D-08. Do not give `NOT_FOUND` or `INVALID_QUERY` payload fields — an empty object member keeps exhaustive `switch` handling honest in Phase 2.

`Result<T>` is the two-member union in the interface block. Name the success member `data` and the failure member `error`.

`GitHubRequestError extends Error`: set `name = "GitHubRequestError"`, `readonly code = "NETWORK"` (typed as the literal, satisfying D-05 while remaining the *thrown* half of the reconciliation above), and an optional `readonly status?: number` present only when an unrecognised HTTP status caused it. Accept `{ status?: number; cause?: unknown }` as a second constructor argument and pass `cause` through to `super`. Do not include any response body in the message — OBS-03 forbids logging bodies and an error message reaches the logs.

`toFailure(response: Response): GitHubFailure | null` implements the status table above. Returning `null` means "not an expected failure" and is the signal for the caller to throw. Parse `x-ratelimit-reset` and `retry-after` with `Number.parseInt` and reject `NaN` before using a value. Compute now-in-seconds as `Math.floor(Date.now() / 1000)`.

`toRequestError(cause: unknown, status?: number): GitHubRequestError` normalises anything thrown by `fetch` or by JSON parsing into the one thrown type. Detect the timeout case by checking `cause instanceof DOMException && cause.name === "TimeoutError"` and give it a message that names the timeout, because that is the failure an operator will need to recognise in the logs. Never interpolate `process.env.GITHUB_TOKEN` or any header into a message.

Write `src/lib/github/errors.test.ts` alongside it with one `it` per bullet in `<behavior>`, named for the behaviour rather than the function per TESTING.md ("maps 403 with an exhausted rate limit to RATE_LIMIT with a reset time"). Build inputs with the real `Response` constructor and real header objects — no hand-rolled fakes — so the test exercises the same header casing behaviour the runtime will. Freeze time with `vi.useFakeTimers()` where a fallback or `retry-after` value is asserted, and restore it in `afterEach`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub REST API → this app | Untrusted third-party JSON and headers cross into typed application state |
| Server process → stdout logs | Secrets can leak by being written, not by being read |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Information disclosure | `log.ts` | mitigate | `GitHubCallLog` is a closed object type with no header, body, or token field — logging a secret is a compile error, not a code-review catch. Test asserts a stubbed token value never appears in any `console.log` argument (OBS-03) |
| T-01-02 | Information disclosure | `errors.ts` | mitigate | `GitHubRequestError` messages are constructed from status and a fixed English string only; response bodies and headers are never interpolated, because error messages reach the same logs |
| T-01-03 | Tampering | `types/github.ts` | accept | GitHub JSON is typed but not runtime-validated in Phase 1. A malformed payload surfaces as a thrown `GitHubRequestError` at parse time in plan 01-02, which is the generic error state. Runtime schema validation would mean a new dependency, which the phase forbids |
| T-01-04 | Repudiation | `log.ts` | mitigate | Every GitHub call gets a `requestId` and a derived `level`, so a failure can be tied to a specific call in stdout |
| T-01-SC | Tampering | npm installs | mitigate | This plan installs **nothing**. `package.json` and `package-lock.json` are not in `files_modified`; any diff to them is a plan violation and must stop for human review before proceeding |
</threat_model>
