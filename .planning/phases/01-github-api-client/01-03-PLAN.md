This plan creates:
- `async function githubFetch<T>(options: GitHubFetchOptions): Promise<Result<T>>`
- `type GitHubFetchOptions = { path: string; endpoint: GitHubEndpointLabel; revalidate: number }`

`path` is a fully-built, already-encoded absolute path with its query string, produced by the calling capability unit (`/search/repositories?q=…` or `/repos/owner/repo`). `githubFetch` never constructs endpoint-specific queries — that ownership sits in the units per the ARCHITECTURE.md boundary table.

`revalidate` is the caller's, but the **cache opt-in is this function's**. The units decide *how stale* is acceptable (60 vs 300); this function decides *that there is a cache at all*. Splitting it that way means a future change to a window cannot accidentally drop the opt-in, and there is exactly one place to look when quota starts disappearing.

    - A 200 response returns `{ ok: true, data }` with the parsed body, and `fetch` was called exactly once.
    - A 403 with `x-ratelimit-remaining: 0` returns `{ ok: false, error: { code: "RATE_LIMIT", resetAt } }` and `fetch` was called exactly once — no retry (OBS-02, AGENTS.md).
    - A 429 behaves identically to the 403 rate-limit case, once, no retry.
    - A 404 returns `{ ok: false, error: { code: "NOT_FOUND" } }`, once, no retry.
    - A 422 returns `{ ok: false, error: { code: "INVALID_QUERY" } }`, once, no retry.
    - A 500 throws `GitHubRequestError` with `status === 500`, and `fetch` was called exactly once — a status response is a response, not a transport fault, so the single-retry allowance does not apply.
    - A 200 with a body that is not valid JSON throws `GitHubRequestError`.
    - A `fetch` that rejects with a `TypeError` is retried exactly once; if the retry succeeds the result is returned; if it also fails a `GitHubRequestError` with `code === "NETWORK"` is thrown, and `fetch` was called exactly twice.
    - A request that exceeds `REQUEST_TIMEOUT_MS` rejects with a `GitHubRequestError` that `toRequestError` classified as a timeout, and it is **not** retried — the underlying call was made exactly once. The mechanism is whichever one plan 01-02's decision line selected; the test asserts the observable outcome, so it stays valid under either.
    - With `GITHUB_TOKEN` stubbed, the outgoing request carries `Authorization: Bearer <token>` and `logUnauthenticatedOnce` does not fire.
    - With `GITHUB_TOKEN` unset or empty, no `Authorization` header is sent and the unauthenticated notice fires.
    - Every outgoing request carries `Accept: application/vnd.github+json`.
    - Exactly one `logGitHubCall` line is emitted per completed call, carrying the status, a positive `durationMs`, and the rate-limit header values; on a thrown failure a line is still emitted with `status: null` and a non-null `errorType`.
    - No captured `console.log` argument contains the stubbed token value.
    - A `path` that does not start with a single `/` — including `//evil.example.com/x` and `https://evil.example.com/x` — throws before any `fetch` occurs.
    - The URL passed to `fetch` always begins with `https://api.github.com/`.

  <action>
Create `src/lib/github/client.ts`. It is the shared HTTP core from the ARCHITECTURE.md boundary table: it may import `errors.ts`, `log.ts`, and `@/types/github`, and it must never import `search.ts` or `repo.ts` or contain endpoint-specific query logic. Open the file with a comment stating it is server-side only and must never be imported by a Client Component — this is the module that reads the token, and that rule is what keeps `GITHUB_TOKEN` out of the browser bundle by construction (API-03, SECURITY.md). Do not add the `server-only` package to enforce it: the phase forbids new production dependencies and that package is not already in the tree.

Module constants: `GITHUB_API_BASE_URL = "https://api.github.com"`, `REQUEST_TIMEOUT_MS = 5000` (the ~5s from the OPERATIONS.md resilience table), `TRANSPORT_RETRY_DELAY_MS = 250`, and the API version header value `2022-11-28`.

URL construction (SEC-03, defence in depth): reject any `path` that does not match a leading single `/` followed by a non-`/` character, throwing a `GitHubRequestError` before any network activity. The units build their own paths with `URLSearchParams` and `encodeURIComponent`, so this guard should never fire in practice — it exists so that if a future edit ever concatenates a user value into `path`, the request cannot be redirected to another origin via a protocol-relative or absolute URL. Then compose with `new URL(path, GITHUB_API_BASE_URL)`.

Headers: always `Accept: application/vnd.github+json` and `X-GitHub-Api-Version: 2022-11-28`. Read `process.env.GITHUB_TOKEN` at call time, not module load — OPERATIONS.md requires the same build artifact to run in any environment. Treat an empty or whitespace-only value as absent. When present, add `Authorization: Bearer <token>`; when absent, call `logUnauthenticatedOnce()` (D-15).

**Fetch options — copy plan 01-02's decision line from `docs/OPERATIONS.md` verbatim and implement exactly that.** Under the expected outcome that is `{ cache: "force-cache", next: { revalidate }, signal: AbortSignal.timeout(REQUEST_TIMEOUT_MS) }`, or the same without the signal if the measurement showed a signal opts the request out of the data cache, in which case the deadline is enforced with `Promise.race` against a timer that rejects with `new DOMException("...", "TimeoutError")` so `toRequestError` still classifies it as a timeout.

Two things are non-negotiable regardless of which branch applies, and both should carry a comment saying why, because both are counter-intuitive enough to be "cleaned up" by a later reader:

1. **`cache: "force-cache"` is required, not redundant.** `next: { revalidate }` alone does not cache in Next 15+ — the default is `auto no cache`, and this route reads request-time APIs, so it refetches on every request. Dropping the `cache` option does not produce an error, a warning, or a failing type check. It produces an app that quietly spends its entire rate limit on repeat renders. That is exactly what D-11a was written to prevent, and it is why there is a test asserting this specific field.
2. **Never pass `cache: "no-store"` alongside `revalidate`.** The docs state conflicting options are both ignored and warn in development — the result is neither caching nor no-store, which is the worst of the three.

Timing: capture `Date.now()` before the attempt and compute `durationMs` on both the success and failure paths.

Retry policy, stated as code and as a comment because the instinct is backwards: never retry any HTTP response, whatever its status — a 403, 429, 404 or 422 is deterministic and retrying a rate limit spends the quota that is already exhausted. Retry at most once, after `TRANSPORT_RETRY_DELAY_MS`, and only when the rejection is a transport fault (`cause instanceof TypeError`). Never retry a `TimeoutError`: the caller has already waited the full deadline and a second wait doubles the time the render is blocked, which is the exact harm the timeout exists to prevent. Log each attempt separately so the retry is visible in stdout.

Response handling, in order: read the rate-limit headers, emit the log line, then branch. `response.ok` → parse JSON and return `{ ok: true, data: parsed as T }`. Otherwise call `toFailure(response)`; a non-null result is returned as `{ ok: false, error }` (D-01, D-02 — these are returned, never thrown). A `null` result means an unrecognised status, so throw via `toRequestError(undefined, response.status)` (D-03). A JSON parse failure throws via `toRequestError`.

Set `cacheHit` to whatever plan 01-02 concluded the runtime can honestly report — `null` if it found no reliable in-process signal. Do not infer it from `durationMs`.

The generic is unchecked by design: `githubFetch<T>` asserts the shape rather than validating it, because runtime validation would need a schema dependency the phase forbids. Note that in a comment beside the cast so it reads as a decision rather than an oversight, and keep the cast confined to this one line — nothing downstream should ever cast again.

Write `src/lib/github/client.test.ts` covering every bullet in `<behavior>`. Mock at the `fetch` boundary per TESTING.md — `vi.stubGlobal("fetch", vi.fn())` with real `Response` objects, never `vi.mock` of the module under test. Assert on the arguments `fetch` received — the URL string, the headers, **and the whole init object's `cache` and `next.revalidate` fields** — to prove the request that went out, and on call counts to prove the retry policy, since "no retry on rate limit" is only provable by counting. Restore with `vi.unstubAllGlobals()` and `vi.unstubAllEnvs()` in `afterEach`. For the timeout test, reject with `new DOMException("The operation timed out.", "TimeoutError")` rather than trying to make a real timer fire.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Caller-supplied `path` → outbound URL | A path string is the only caller-controlled input that decides which origin and endpoint is addressed |
| Server environment → outbound request | `GITHUB_TOKEN` crosses from the environment into a request header and must cross nowhere else |
| GitHub response → application state | Third-party JSON and headers become typed values and log fields |
| Test-time base URL edit → shipped source | A temporary change made to measure something must not survive as configuration |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-05 | Tampering | `githubFetch` URL construction | mitigate | Reject any `path` not matching a leading single `/` followed by a non-`/`, before any fetch.
