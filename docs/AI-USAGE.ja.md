# AI 利用記録

本プロジェクトにおける AI の利用方法を工程ごとに記録したものです。英語版は [AI-USAGE.en.md](./AI-USAGE.en.md) にあります（内容は同一です）。

## 運用ルール

**この記録の読み手:** 本課題をレビューする担当エンジニア。評価対象は判断の内容である。「何をしたか」だけの記録では判断を示せない。**理由こそが評価の材料**となる。

- **1 工程が完了するたびに、このファイルと英語版の両方へ追記する。** 当該工程をコミットする前に必ず更新すること。
- 各エントリには次を必ず含める：工程番号・日付・使用した AI ツール・AI に任せた範囲・**その方針を採った理由（検討したうえで採用しなかった選択肢とその理由を含む）**・人間が判断した範囲・レビュー方法（実行したコマンドと結果を具体的に）。
- AI の出力をそのまま採用したか、修正したかを正直に記載する。修正した場合は何が誤っていたかも記載する。
- 記録は後からまとめて書かず、その工程のうちに書く。

**理由が分からない場合は、推測せず開発者に確認する。** もっともらしいが事実でない理由は、記載しないより悪い。読み手には説得力があるように見え、レビュアーには真偽を確かめる手段がなく、面接で本人に尋ねた際の回答と食い違う。本記録に書かれている理由は、すべて開発者自身が述べたものである。

エントリは、「なぜこの実装にしたのか」がその記述だけで読み手に伝わる状態になって初めて完成とする。

### `AGENTS.md` を置く理由

Claude Code は各セッションの開始時に `AGENTS.md`（`CLAUDE.md` 経由）を自動的に読み込む。これがないと、セッションごとにプロジェクトの規約を推測し直すことになり、方針がぶれる。とくに危険なのは「詳細画面はモーダルではなくページとして実装する」のような、コードを見ただけでは分からない制約である。ルールをリポジトリ内に置くことで、セッションをまたいで維持でき、他のファイルと同様にレビューの対象にできる。

### エージェントを限定している理由

グローバル設定には他プロジェクト向けの多数のエージェント・スキル（計画支援、マーケティング、モバイル等）が含まれるが、本プロジェクトには不要でノイズとコストになる。そのため `AGENTS.md` では、実際に有用な範囲（コード探索、設計、TDD、デバッグ、完了前の検証、ブラウザでの動作確認）に限定して明記している。あわせて、エージェントはプロジェクトの制約を必ず引き継ぐこと、およびエージェントの報告は鵜呑みにせずローカルで再検証することを規定している。

### 計画フレームワークに GSD を採用した理由

`.planning/` 配下の計画ドキュメントは、GSD（Get Shit Done）という構造化ワークフローフレームワークを用いて作成した。採用は開発者自身の判断であり、理由は以下のとおり。

- **本リポジトリにおけるプロジェクト管理ツールとして機能する。** 現時点ではローカル限定のプロジェクトであり、背後に Jira のようなボードは存在しない。GSD の `REQUIREMENTS.md` / `ROADMAP.md` / `STATE.md` がその役割を果たし、要件・フェーズ・現在の状態をコードと同じくバージョン管理下で追跡できる。
- **将来的に実際の PM ツールへ移行できる。** GSD は後から Jira や Notion と連携でき、プロダクトマネージャーが普段使っているツールでチケットを書けば、GSD が各チケットを実行可能な計画へ変換する。今この方式を選んでも、チーム開発に移行する際にプロセスを作り直す必要がない。
- **プロトタイプではなく、プロダクション運用を前提に設計されている。** 大手企業のエンジニアが採用しているのは、計画・実行・検証の各段階で品質を担保し、モデルの場当たり的な出力に任せないためである。
- **コードレビュー機能が優れている。** 生成されたコードを無条件に信頼せず、レビューを通過して初めて採用する運用にできる。
- **前提を勝手に置かない。** これが決め手となった。不確かな点があれば、推測して進めるのではなく既定で確認する。本記録が求めている姿勢（`AGENTS.md` の「理由が不明な場合は確認する」）と同じである。
- **出力を自動的に検証する。** 検証は人手で思い出して行うものではなく、ワークフローに組み込まれた工程として実行される。計画は実行前にフェーズ目標を達成できるか検証され、完了した作業は充足を主張した要件に対して検証され、要件とフェーズの対応漏れは推測ではなく確認によって担保され、生成されたドキュメントは実際のコードベースと突き合わせて事実確認される。生成物は「完成した成果」ではなく「検証すべき主張」として扱われる。

要するに、スクラムチームと同じ進行と品質ゲートを備えたうえで、その構成員が AI であるという形になっている。プロダクションを想定した実装が評価対象である本課題において、開発プロセス自体が構造化されていることを示すのは、余分な手間ではなく評価材料の一部だと考えた。

### スコープに関する補足

課題文は短く、この種の課題では「見栄えのする要素」（データベース、認証、キャッシュ基盤など）を足したくなる。それぞれについて検討したうえで採用を見送り、その理由を `docs/ARCHITECTURE.md` と `.planning/PROJECT.md` に明記した。不要な構成要素はレビューにおいて中立ではなく、「なぜこれが必要なのか」という指摘を招く。本件においてその問いへの正直な答えは「必要ない」であるため、採用しなかった。

## 工程 4: アーキテクチャドキュメント・境界設計・テスト方針の整備

  - 本アプリは読み取り専用であり、作成・更新・削除の操作は存在しない（データは GitHub 側が保持）。したがってプロダクション品質の要点はアプリケーションの複雑さではなく、CI とテストにある。アーキテクチャドキュメントの役割は、存在しない複雑なロジックを説明することではなく、境界を読み取れる形で示し、分離が適切であることを示すことにある。
  - GitHub と接する部分は、共有かつ状態を持たない HTTP・エラー処理コアの上に、検索ユニットとリポジトリユニットを分離して配置した。各ユニットが独立して差し替え可能であり、互いに直接参照しないため、一方のエンドポイントの変更が他方へ波及しない。検証できない境界は境界として機能しないため、ルールとして明文化した。
  - コードがまだスキャフォールドの段階で目標設計を記述すると、実装済みの範囲を過大に見せてしまう恐れがある。「スキャフォールドの現状のみを記述する（設計意図が失われる）」「目標設計のみを記述する（進捗を過大に見せる）」のいずれでもなく、各部分に実装状況を明示する方式を採用した。
- **人間が判断した範囲:**
  - 9 種類のドキュメント一式の生成は見送った。スキャフォールド段階では大半が内容の乏しいものになるため、実質的な情報を持つアーキテクチャとテストの 2 点に絞った。
  - 境界は明確な分離として示しつつ、「サービス分割の候補である」といった記述は一切行わない方針とした。重要なのは構造上の性質であり、将来のデプロイ構成の推測は不要な記述になる。
  - ドキュメントが完成度を過大に示さないよう、実装状況を明示する方式を選択した。
- **レビュー方法:** `npm run lint` / `npm run typecheck` / `npm run test:coverage` / `npm audit` がすべて成功することを確認。ドキュメント内の CI ジョブ名は `.github/workflows/ci.yml` と 1 行ずつ突き合わせ、6 件すべて一致することを確認。Mermaid の図は GitHub が使用するバージョンである mermaid 11 で解析し、5 点すべて有効であることを確認した。
- **そのまま採用したか、修正したか:** いずれのサブエージェントの出力も無条件では採用せず、検証した結果 3 点の修正が必要だった。両エージェントとも図は有効であると報告したが、最初の検証では 5 点中 3 点が失敗した。原因は図ではなく検証環境側の不備であり、修正して再実行したところ 5 点すべて成功した。また、修正前のアーキテクチャドキュメントには実在しない `security` という CI ジョブが記載されていたため、実際の 6 ジョブに修正した。最も有用だったのは、テスト担当エージェントが `vitest.config.mts` の実際の不具合を検出したことである。カバレッジ設定が `*.spec` ファイルをテストとして収集する一方、計測対象ソースからは除外していなかったため、当該ファイルが「完全にカバーされたコード」として計上され、カバレッジ値が実態より高く出る状態だった。これを修正し、あわせて `AGENTS.md` と `README.md` が実際のスクリプト構成・ディレクトリ構成と乖離していた 3 箇所も修正した。

## 工程 5: 運用・セキュリティドキュメントの整備と Node.js のアップグレード

- **日付:** 2026-08-01
- **使用ツール:** Claude Code (Claude Opus 5)
- **AI に任せた範囲:**
  - プロダクション運用に必要でありながら未記載だった項目を洗い出し、`docs/OPERATIONS.md`（可観測性、レート制限の監視、タイムアウトとリトライの方針）および `docs/SECURITY.md`（脅威モデル、トークンの取り扱い、レスポンスヘッダー、プライバシー）を作成した。
  - 可観測性・セキュリティ・多言語対応・ドキュメントに関する要件を 10 件追加し、ロードマップの各フェーズへ反映したうえで、整合性を自動で検証した。
  - CI を再構成し、3 つのジョブが同一のビルドを重複して実行していた状態から、ビルドを 1 回だけ行って成果物を共有する方式へ変更した。
  - 実行環境を Node 20.20.1 から 24.18.1 へ更新し、`engines` による制約を追加した。
- **その方針を採った理由:**
  - 可観測性が全く記載されていなかった。これは見た目以上に重要で、本アプリの主要な障害要因はコードの不具合ではなく GitHub のレート制限の枯渇であり、残りクォータは各レスポンスのヘッダーに既に含まれている。これを記録することで、障害発生時点だけでなく、その前段階の劣化を把握できる。
  - 耐障害性には具体的な欠落があった。`fetch()` は既定でタイムアウトを持たず、上流が応答しない場合にレンダリングを無期限に保持してしまう。あわせて「レート制限時はリトライしない」というルールを明記した。直感とは逆であり、既に尽きているクォータをさらに消費して復旧を遅らせるためである。
  - Node 20 は 2026 年 4 月にサポートが終了し、セキュリティ更新を受けられない。プロダクションを想定した実装を掲げる以上、サポート切れの実行環境を固定したままにはできず、これは 1 ファイルを見れば分かる事実である。Node 24 は 2028 年までサポートされる。
  - 可観測性のツールは無償かつ自前で動かせるものに限定し、既定を標準出力への構造化ログとした。これによりアプリケーションは引き続き外部サービスなしで動作する。コレクタやコンテナを必要とする構成は任意であり、動作の前提条件にはしない。
- **人間が判断した範囲:**
  - ツールは無償かつローカルで動作するものに限る方針を指示した。これによりホスティング型のエラー追跡・監視サービスは対象外となった。
  - UI は日本語、コード・コメント・コミットは英語とする方針を決定した。この点は未記録であり、最初の UI 実装の着手を妨げる状態だった。
  - CI のビルド共有については、「誤りではないが無駄がある」と指摘した結果、修正を指示した。
  - Node のアップグレードを承認した。

## 工程 6: GitHub API クライアント — 型付き境界、計測に基づくキャッシュ、そして強制されるルール

- **日付:** 2026-08-02
- **使用ツール:** Claude Code (Claude Opus 5)。GSD の計画・実行ワークフローを 5 つの計画に分けて使用。
- **AI に任せた範囲:**
  - GitHub 境界の実装一式：`src/types/github.ts` および `src/lib/github/{errors,log,client,search,repo}.ts`。テストは各モジュールと同じ場所に配置。テスト 113 件、`src/lib/github/` の行・分岐・関数カバレッジはいずれも 100%。
  - クライアントを書く**前に**、Next 16 の fetch キャッシュの挙動をローカルのカウント用サーバーに対して実測。実装後、出荷したクライアント自身に対して同じ計測を再実施。
  - `docs/ARCHITECTURE.md` / `docs/OPERATIONS.md` / `docs/TESTING.md` およびロードマップのフェーズ 1 成功基準を、実際に作られたものと突き合わせて修正。これらは方針が確定する前に書かれており、最終的に 4 箇所が事実と異なる状態になっていた。
  - これまで「レビューで担保」としていた 2 つのルールを ESLint ルールとして実装し、各ルールが禁止対象のコードに対して実際にエラーを報告することを証明するテストを作成。
- **その方針を採った理由:**
  - **失敗の扱いはハイブリッド方式であり、これが本フェーズで最も重要な判断である。** レート制限・未検出・不正なクエリは**戻り値**として返し、呼び出し元のページが描画する。例外として**投げる**のは、通信障害・5 秒のタイムアウト・すべての 5xx・不正な JSON のみ。理由は具体的である。本番環境では、Next はサーバー側のエラーをクライアントのエラーバウンダリに渡す前に無害化する。したがって `error.tsx` の内部でエラーの型によって分岐する処理は信頼できない。状態ごとの UI（再試行可能時刻を伴うレート制限の表示と、「キーワードを見直してください」の表示）は開発環境では動作し、デプロイ後に無言で汎用メッセージ 1 種類に退化する。これは本番でしか現れない不具合であり、設計段階で作り込むべきではない。`NETWORK` だけは分岐を必要としない——汎用の再試行メッセージが完全な答えになる——ため、これのみを例外として投げている。
    - **採用しなかった案：すべての失敗を例外として投げ、`error.tsx` で型によって分岐する。** 一見単純だが、確認できない場所で破綻する。課題が重視しているレート制限と「該当なし」の区別が、デプロイ後には 1 種類のメッセージに潰れてしまう。
  - **ログはロギングライブラリではなく `console.log` と `JSON.stringify` で出力する。** 上流が 1 つだけの読み取り専用アプリに、ログレベル・トランスポート・秘匿情報のマスキング機構は不要であり、Next は既に標準出力へ書き込んでいる。ログエントリの型は**閉じている**ため、トークンやヘッダー一式を書き込め得るフィールドがそもそも存在しない。これはコンパイル時の保証であり、設定を忘れうるマスキング規則より強い。
    - **採用しなかった案：`pino`。** 依存関係と、追随すべきバージョンと、`npm audit` の対象が 1 つ増えるだけで、得られるものがない。あわせて記録しておくと、将来ログ基盤へ移行する場合もライブラリは不要である。標準出力の JSON はそのまま転送できるため、これはインフラ側の変更であってコードの変更ではない。
  - **キャッシュ設定は推測ではなく実測で決めた。** レビュアーにとって最も参考になるのはこの点だと考える。当初の計画はフレームワークのドキュメントに基づいて fetch のオプションを指定していたが、その根拠は誤っていた。素の Node によるカウント用サーバーと一時的な動的ルートを用意し、上流への実リクエスト数を数えたところ、`{ next: { revalidate: 60 } }` だけで**キャッシュされる**（3 回のレンダリングに対し上流へのリクエストは 1 回）。これは計画が前提としていた内容と矛盾する。それでも結論は変わらず `cache: "force-cache"` を明示して出荷している。これはドキュメントが示す意図の正式な表記であり、呼び出し箇所で意図を明示でき、将来 `revalidate` が `0` や条件付きに変わっても意図が残るためである。誤っていた前提と、なお有効な結論の双方を `docs/OPERATIONS.md` に記載した。黙って修正するのではなく、後から読む人がどこを信用してよいか判断できるようにするためである。
    - **計測は途中で自前の否定対照（ネガティブコントロール）を追加した。ここが読む価値のある部分である。** 計画していた 4 条件すべてが「キャッシュされた」と出た時点で、その結果は「サーバーに 2 回目以降到達していない壊れた計測器」と区別がつかない。壊れた計測器でも同じ出力になるからである。そこで、ドキュメント上キャッシュされないはずの条件を 2 つ追加した（キャッシュ関連オプションを一切指定しない場合と、`cache: "no-store"` の場合）。いずれも 3 回とも上流に到達した。ここで初めて肯定側の結果に意味が生まれた。これがなければ、検証されていない計測器を根拠に記録済みの決定を覆すことになり、それはまさにこの計測が防ごうとしていた失敗そのものだった。
    - その後、**出荷したクライアント自身**に対して同じ計測を行った。オプションが正しくても関数がキャッシュしない可能性はあるためである。実際のルートを 6 回描画し、上流へのリクエストは 1 回。この実測こそがキャッシュ要件の唯一の証拠であり、ユニットテストの成功はその代わりにはならない。
  - **キャッシュの有効期間は 2 種類——検索は 60 秒、詳細は 300 秒。** 検索結果はリポジトリの作成やスターによって変動するが、詳細情報の変化は緩やかで、レビュー中に最も再読み込みされやすいページでもある。単一の値ではどちらかが必ず不適切になる。またキャッシュを有効にする指定自体はクライアント側が持ち、2 つのユニットは有効期間だけを渡す。したがって将来この値を変更してもキャッシュを誤って外すことはできない。
  - **1 ページあたり 20 件。** スクロールが延々と続かない程度に十分な件数で、ペイロードも小さく、GitHub の 1000 件上限の内側でページングを自然に確認できる。GitHub 既定の 30 件は、本件では利点なくスクロールを長くするだけである。
  - **ウォッチャー数は `watchers_count` ではなく `subscribers_count` から取得する。** GitHub の REST API において `watchers_count` は `stargazers_count` の複製である。課題ではスター数とウォッチャー数が別々の必須項目として指定されているため、一見正しそうなフィールドを使うと同じ数値が 2 箇所に表示され、不具合に見える。実際のウォッチャー数は `subscribers_count` であり、詳細エンドポイントにしか存在しない。ドメイン型には `watchersCount` というメンバー自体を設けていないため、`watchers` を埋める方法は意図的なマッピング以外に存在しない。この罠はコメントではなく型によって塞いでいる。

    - **採用しなかった案：環境変数で変更可能なベース URL。**「テスト専用」のエクスポートやコンストラクタ引数も同様に不可とした。攻撃側はその仕組みが何のために追加されたかを考慮しないためである。これは 1 つの変数だけで成立するトークン漏洩経路であり、環境変数を設定できる者は `Authorization` ヘッダー——本アプリ唯一の秘密情報——を任意のホストへ向けられる。確認用の計測では、代わりにソースを一時的に 1 行だけ書き換え、バックアップから復元して `diff` でバイト単位の一致を確認した。得られるカバレッジは同一で、攻撃面は増えない。
