## 工程 2: プロジェクトルール（`AGENTS.md`）と AI 記録ワークフローの整備

- **日付:** 2026-08-01
- **使用ツール:** Claude Code (Claude Opus 5)
- **AI に任せた範囲:**
  - リポジトリのルールファイルである `AGENTS.md` を作成。内容は、課題要件（変更不可の制約）、ビルド・テストコマンド、技術スタック、コーディング規約（TypeScript、React / Next.js の方針、命名規則、ディレクトリ構成）、必須のエラー・エッジケース処理、GitHub API の利用ルールとレート制限、テスト方針、Git 運用、および明示的な禁止事項の一覧。
  - 失われやすい依存関係の判断を記録：`package.json` の `overrides` を入れた理由と、npm の `overrides` は既存のツリーには適用されずクリーン再インストールが必要である点。
  - 本プロジェクトで使用するエージェントと、あえて使用しないエージェントを明文化（下記参照）。
  - 2 ファイル構成の AI 利用記録と、「各工程はコミット前に両ファイルへ追記する」というルールを整備。
- **人間が判断した範囲:**
  - AI の利用状況は最後にまとめて書くのではなく、**工程ごとに記録する**方針とした。実際の進め方をそのまま残すため。
  - 提出用の日本語版と、英語版の 2 つを維持する方針とした。
  - `AGENTS.md` は英語で記述する方針とした。これはレビュアー向けではなくエージェント向けの文書であり、英語のほうが処理が速くコストも低いため。提出用の文書は本来の言語のまま維持する。
- **レビュー方法:** 記載したルールが課題要件と矛盾しないことを確認。本工程ではアプリケーションコードの変更は行っていない。

### `AGENTS.md` を置く理由

Claude Code は各セッションの開始時に `AGENTS.md`（`CLAUDE.md` 経由）を自動的に読み込む。これがないと、セッションごとにプロジェクトの規約を推測し直すことになり、方針がぶれる。とくに危険なのは「詳細画面はモーダルではなくページとして実装する」のような、コードを見ただけでは分からない制約である。ルールをリポジトリ内に置くことで、セッションをまたいで維持でき、他のファイルと同様にレビューの対象にできる。

### エージェントを限定している理由

グローバル設定には他プロジェクト向けの多数のエージェント・スキル（計画支援、マーケティング、モバイル等）が含まれるが、本プロジェクトには不要でノイズとコストになる。そのため `AGENTS.md` では、実際に有用な範囲（コード探索、設計、TDD、デバッグ、完了前の検証、ブラウザでの動作確認）に限定して明記している。あわせて、エージェントはプロジェクトの制約を必ず引き継ぐこと、およびエージェントの報告は鵜呑みにせずローカルで再検証することを規定している。

## 工程 3: アーキテクチャ設計・計画ドキュメント・CI 品質ゲートの整備

- **日付:** 2026-08-01
- **使用ツール:** Claude Code (Claude Opus 5)。ロードマップ生成には専用のサブエージェントを 1 つ使用。
- **AI に任せた範囲:**
  - 課題文を再度読み込み、「何が書かれていないか」を確認。認証・データベース・永続化・デプロイ・期限のいずれについても記載がないことを確認し、これらは実装しない方針とした。
  - `docs/ARCHITECTURE.md` を作成。システム構成、ディレクトリ構成、主要な設計判断とその理由、採用しなかった選択肢とその理由の一覧、ローカル開発手順を記載。
  - CI 品質ゲートを作成。`.github/workflows/ci.yml`（Lint、型チェック、カバレッジ付きユニットテスト、ビルド、Playwright による E2E、axe によるアクセシビリティ検査、`npm audit`、gitleaks によるシークレット検査、CodeQL による SAST）および `.github/dependabot.yml`。
  - CI が前提とする実行環境の整備：Playwright 設定、E2E スモークテスト、アクセシビリティテスト、Vitest のカバレッジ閾値、`.env.example`。
  - 計画ドキュメント一式を作成：`.planning/PROJECT.md`、`REQUIREMENTS.md`（v1 要件 34 件）、`config.json`、`ROADMAP.md`、`STATE.md`。ロードマップは専用サブエージェントが要件から生成。
- **人間が判断した範囲:**
  - **MongoDB の採用を見送った。** 「ローカルで完結させるため」という案が出たが、本アプリに永続化すべきデータは存在せず（データは GitHub 側が保持）、現状すでに外部サービス不要で起動できる。DB を追加するとローカル環境はむしろ複雑になり、レビュアーには過剰設計と映る。
  - **ユーザー認証は実装しない。** 課題文に記載がなく、公開リポジトリの検索に認証は不要。
  - **DAST は実施しない。** 稼働環境が必要であり、認証・セッション・データストアのない本アプリでは HTTP ヘッダー設定程度しか検出されない。v2 の項目として記録するに留めた。
  - スコープ方針：課題要件に加え、レビューで実際に評価される品質面のみを対象とし、独自機能は追加しない。
  - ロードマップの粒度は粗め（coarse）とし、フェーズごとの調査エージェントは無効化した。対象ドメインが小さく、既に十分把握できているため。
- **レビュー方法:** `npm run lint` / `npm run typecheck` / `npm run test:coverage` / `npm run test:e2e` / `npm run test:a11y` をローカルで実行し、すべて成功することを確認。`npm audit` の検出件数は 0 件。
- **そのまま採用したか、修正したか:** サブエージェントが生成したロードマップは 1 点修正のうえ採用した。CI 関連要件が単に「完了」と記載されていたが、GitHub リモート未設定のためワークフローは一度も実行されていない。「各スクリプトはローカルで成功済み。ワークフロー自体は初回 push まで未検証」と正確な記述に修正した。

### スコープに関する補足

課題文は短く、この種の課題では「見栄えのする要素」（データベース、認証、キャッシュ基盤など）を足したくなる。それぞれについて検討したうえで採用を見送り、その理由を `docs/ARCHITECTURE.md` と `.planning/PROJECT.md` に明記した。不要な構成要素はレビューにおいて中立ではなく、「なぜこれが必要なのか」という指摘を招く。本件においてその問いへの正直な答えは「必要ない」であるため、採用しなかった。
