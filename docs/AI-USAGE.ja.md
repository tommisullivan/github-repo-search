# AI 利用記録

本プロジェクトにおける AI の利用方法を工程ごとに記録したものです。英語版は [AI-USAGE.en.md](./AI-USAGE.en.md) にあります（内容は同一です）。

## 運用ルール

**この記録の読み手:** 本課題をレビューする担当エンジニア。評価対象は判断の内容である。「何をしたか」だけの記録では判断を示せない。**理由こそが評価の材料**となる。

- **1 工程が完了するたびに、このファイルと英語版の両方へ追記する。** 当該工程をコミットする前に必ず更新すること。
- 各エントリには次を必ず含める：工程番号・日付・使用した AI ツール・AI に任せた範囲・**その方針を採った理由（検討したうえで採用しなかった選択肢とその理由を含む）**・人間が判断した範囲・レビュー方法（実行したコマンドと結果を具体的に）。
- AI の出力をそのまま採用したか、修正したかを正直に記載する。修正した場合は何が誤っていたかも記載する。
- 記録は後からまとめて書かず、その工程のうちに書く。

**理由が分からない場合は、推測せず開発者に確認する。** もっともらしいが事実でない理由は、記載しないより悪い。読み手には説得力があるように見え、レビュアーには真偽を確かめる手段がなく、面接で本人に尋ねた際の回答と食い違う。本記録に書かれている理由は、すべて開発者自身が述べたものである。

エントリは、「なぜこの実装にしたのか」がその記述だけで読み手に伝わる状態になって初めて完成とする。

### `AGENTS.md` を置く理由

Claude Code は各セッションの開始時に `AGENTS.md`（`CLAUDE.md` 経由）を自動的に読み込む。これがないと、セッションごとにプロジェクトの規約を推測し直すことになり、方針がぶれる。とくに危険なのは「詳細画面はモーダルではなくページとして実装する」のような、コードを見ただけでは分からない制約である。ルールをリポジトリ内に置くことで、セッションをまたいで維持でき、他のファイルと同様にレビューの対象にできる。

### エージェントを限定している理由

グローバル設定には他プロジェクト向けの多数のエージェント・スキル（計画支援、マーケティング、モバイル等）が含まれるが、本プロジェクトには不要でノイズとコストになる。そのため `AGENTS.md` では、実際に有用な範囲（コード探索、設計、TDD、デバッグ、完了前の検証、ブラウザでの動作確認）に限定して明記している。あわせて、エージェントはプロジェクトの制約を必ず引き継ぐこと、およびエージェントの報告は鵜呑みにせずローカルで再検証することを規定している。

### 計画フレームワークに GSD を採用した理由

`.planning/` 配下の計画ドキュメントは、GSD（Get Shit Done）という構造化ワークフローフレームワークを用いて作成した。採用は開発者自身の判断であり、理由は以下のとおり。

- **本リポジトリにおけるプロジェクト管理ツールとして機能する。** 現時点ではローカル限定のプロジェクトであり、背後に Jira のようなボードは存在しない。GSD の `REQUIREMENTS.md` / `ROADMAP.md` / `STATE.md` がその役割を果たし、要件・フェーズ・現在の状態をコードと同じくバージョン管理下で追跡できる。
- **将来的に実際の PM ツールへ移行できる。** GSD は後から Jira や Notion と連携でき、プロダクトマネージャーが普段使っているツールでチケットを書けば、GSD が各チケットを実行可能な計画へ変換する。今この方式を選んでも、チーム開発に移行する際にプロセスを作り直す必要がない。
- **プロトタイプではなく、プロダクション運用を前提に設計されている。** 大手企業のエンジニアが採用しているのは、計画・実行・検証の各段階で品質を担保し、モデルの場当たり的な出力に任せないためである。
- **コードレビュー機能が優れている。** 生成されたコードを無条件に信頼せず、レビューを通過して初めて採用する運用にできる。
- **前提を勝手に置かない。** これが決め手となった。不確かな点があれば、推測して進めるのではなく既定で確認する。本記録が求めている姿勢（`AGENTS.md` の「理由が不明な場合は確認する」）と同じである。
- **出力を自動的に検証する。** 検証は人手で思い出して行うものではなく、ワークフローに組み込まれた工程として実行される。計画は実行前にフェーズ目標を達成できるか検証され、完了した作業は充足を主張した要件に対して検証され、要件とフェーズの対応漏れは推測ではなく確認によって担保され、生成されたドキュメントは実際のコードベースと突き合わせて事実確認される。生成物は「完成した成果」ではなく「検証すべき主張」として扱われる。

要するに、スクラムチームと同じ進行と品質ゲートを備えたうえで、その構成員が AI であるという形になっている。プロダクションを想定した実装が評価対象である本課題において、開発プロセス自体が構造化されていることを示すのは、余分な手間ではなく評価材料の一部だと考えた。

### スコープに関する補足

課題文は短く、この種の課題では「見栄えのする要素」（データベース、認証、キャッシュ基盤など）を足したくなる。それぞれについて検討したうえで採用を見送り、その理由を `docs/ARCHITECTURE.md` と `.planning/PROJECT.md` に明記した。不要な構成要素はレビューにおいて中立ではなく、「なぜこれが必要なのか」という指摘を招く。本件においてその問いへの正直な答えは「必要ない」であるため、採用しなかった。

  - コードがまだスキャフォールドの段階で目標設計を記述すると、実装済みの範囲を過大に見せてしまう恐れがある。「スキャフォールドの現状のみを記述する（設計意図が失われる）」「目標設計のみを記述する（進捗を過大に見せる）」のいずれでもなく、各部分に実装状況を明示する方式を採用した。
- **人間が判断した範囲:**

## 工程 5: 運用・セキュリティドキュメントの整備と Node.js のアップグレード

- **日付:** 2026-08-01
- **使用ツール:** Claude Code (Claude Opus 5)
- **AI に任せた範囲:**
  - プロダクション運用に必要でありながら未記載だった項目を洗い出し、`docs/OPERATIONS.md`（可観測性、レート制限の監視、タイムアウトとリトライの方針）および `docs/SECURITY.md`（脅威モデル、トークンの取り扱い、レスポンスヘッダー、プライバシー）を作成した。
  - 可観測性・セキュリティ・多言語対応・ドキュメントに関する要件を 10 件追加し、ロードマップの各フェーズへ反映したうえで、整合性を自動で検証した。
  - CI を再構成し、3 つのジョブが同一のビルドを重複して実行していた状態から、ビルドを 1 回だけ行って成果物を共有する方式へ変更した。
  - 実行環境を Node 20.20.1 から 24.18.1 へ更新し、`engines` による制約を追加した。
- **その方針を採った理由:**
  - 可観測性が全く記載されていなかった。これは見た目以上に重要で、本アプリの主要な障害要因はコードの不具合ではなく GitHub のレート制限の枯渇であり、残りクォータは各レスポンスのヘッダーに既に含まれている。これを記録することで、障害発生時点だけでなく、その前段階の劣化を把握できる。
  - 耐障害性には具体的な欠落があった。`fetch()` は既定でタイムアウトを持たず、上流が応答しない場合にレンダリングを無期限に保持してしまう。あわせて「レート制限時はリトライしない」というルールを明記した。直感とは逆であり、既に尽きているクォータをさらに消費して復旧を遅らせるためである。
  - Node 20 は 2026 年 4 月にサポートが終了し、セキュリティ更新を受けられない。プロダクションを想定した実装を掲げる以上、サポート切れの実行環境を固定したままにはできず、これは 1 ファイルを見れば分かる事実である。Node 24 は 2028 年までサポートされる。
  - 可観測性のツールは無償かつ自前で動かせるものに限定し、既定を標準出力への構造化ログとした。これによりアプリケーションは引き続き外部サービスなしで動作する。コレクタやコンテナを必要とする構成は任意であり、動作の前提条件にはしない。
- **人間が判断した範囲:**

  - 各描画状態（読み込み中、成功、空、レート制限、2 種類の invalid-query、送出されたネットワーク障害）をそれぞれ独自の ARIA ロールを持つコンポーネントで表現し、状態が互いに混同されないようテストで担保した：空状態のテストは `role="alert"` が存在しないことを確認し、レート制限のテストは空状態の文言が存在しないことを確認し、送出テストは描画そのものが reject し、ページで捕捉されないことを確認する。
- **なぜこのアプローチを採ったか:**
  - **URL が状態であり、ページはサーバーコンポーネントである。** キーワードとページは `?q=…&page=…` に格納する。ロードマップの SRCH-03 が「共有・リロードされたリンクが同じ結果を描画すること」を要求しているためである。送信時に fetch してメモリに保持する状態モデルはリロードで失敗し、`sessionStorage` に保持するモデルは共有リンクで失敗する。両方に耐えるのは URL だけである。したがってページは `searchParams` を読み、`searchRepositories` をサーバー側で呼び出す — クライアントバンドルは GitHub と通信しないため、任意設定の `GITHUB_TOKEN` がブラウザに到達することもない。
    - **却下: ローカル状態を用いた送信時 fetch。** リロード、共有、戻るボタンで失敗する。ロードマップはこの URL-as-state 特性を明示的に評価対象としている。
    - **却下: `sessionStorage` を用いた送信時 fetch。** リロードには耐えるが共有リンクでは失敗し、誰も要求していないストアが追加される。
  - **デバウンスは `setTimeout` と `clearTimeout` であり、ライブラリではない。** `AGENTS.md` は「ライブラリよりプラットフォームを優先せよ」と定める。`use-debounce` や `lodash.debounce` は 12 行に収まる処理のために依存関係、更新対象のバージョン、`npm audit` の項目を増やす。
    - **却下: `useDeferredValue` 単独。** React のスケジューラーに依存するデバウンスとなり、テストが `vi.advanceTimersByTime` で駆動できない。制御可能な遅延こそが目的である — SRCH-05 の主張は「キーストロークの連打で URL 変更が正確に 1 回だけ発生すること」であり、「正確に 1 回」を確実にアサートする唯一の方法は決定論的なタイマーである。
  - **デバウンス更新には `router.replace` を用い、`router.push` は用いない。** キーストロークごとに push すると、ブラウザ履歴が 1 打鍵につき 1 URL で埋まり、戻るボタンで 1 つずつ辿ることになる — レビュアーが手動確認したときだけ露見する UX バグである。
  - **ページはクライアント呼び出しを `try`/`catch` しない。** フェーズ 1 の契約は意図的にハイブリッドである:想定内の失敗（レート制限、invalid query）は値として **返却** されページが描画するが、通信障害、タイムアウト、5xx は **送出** される — App Router の `error.tsx` こそが受け止めるべき場所であり、本番環境では Next がサーバーエラーをサニタイズするため `error.tsx` 内で型による分岐は信頼できない。ページの `try`/`catch` はその契約を無言で破壊してしまう。この点は、クライアントを送出するようモックしてページ描画自体が reject することを確認するテストで担保している。
  - **`INVALID_QUERY` の 2 原因はクライアントではなく、ページで区別する。** フェーズ 1 の `Result` では「空キーワード」と「51 ページ目以降」を区別できず、また区別をクライアントに求めるとページ概念の知識が本来知るべきでないモジュールに漏れる。ページはクライアント呼び出しの **前** にガードを実行し、日本語の別コピーを選ぶ — 「キーワードを入力してください」と「検索できるページを超えています」。ページ上限はクライアントが公開する定数から導出しており（`SEARCH_MAX_RESULTS / SEARCH_PER_PAGE`）、リテラル `50` は書かない。

## 工程 11: 実際に触って見つかった 4 つの UX 欠陥 — 上下 2 か所のページ送り、本物のページ数、スター数順の並び替え、そして最初から無かったアバター

- **なぜこの方法か:**
  - **`sort` を 4 か所に足すのではなく、URL 生成を 1 つに集約した（`src/lib/searchUrl.ts`）。** 入力欄・並び替えコントロール・上下 2 つのページ送り・詳細ページへの戻りリンクは、いずれも検索 URL を組み立てる。手書きのテンプレート文字列 4 か所にパラメータを足す方式には、静かで具体的な失敗モードがある — 並び替えてから 次へ を押すと、ページ送りリンクが `sort` を知らないので並び替えが消える。このモジュールは意図的にフレームワーク非依存とし、Client Component と Server Component が単一の定義を共有できるようにした。`SearchSort` をサーバー専用の `lib/github/search.ts` ではなくここに置いたのも同じ理由である。

## 工程 12: 誤って帰属させた判断の訂正と、本プロジェクトを生んだワークフローの記録

- **日付:** 2026-08-02
- **ツール:** Claude Opus 5（1M コンテキスト）
- **AI に任せたこと:** MongoDB の帰属を 4 箇所で訂正（`README.md` の 2 言語、本ファイルと日本語版それぞれ 2 箇所）。あわせて README に 3 つの節を両言語で追加した — GSD Pi のワークフローと採用理由、補完としての Superpowers スキル群、未実装の自動化構想（Jira / Notion、AI コードレビュー）。
- **なぜこの方法か:**
  - **訂正こそが本題であり、それを起こしたのは開発者である。** ログは MongoDB の却下を「開発者自身の、促されていない判断」と記していた。しかもそれは「選択肢が引かれる空間そのものを形作ったという意味で、より強い証拠である」と明示的に前置きされたリストの中にあった。開発者はこれを読み、事実と異なると述べた — DB を外すという論拠を持ち出したのは AI であり、自分は「結局 API を呼ぶだけだから」として同意しただけである、と。放置すれば、人間の貢献に関するログ中もっとも見栄えのする主張が、そのまま偽の主張になっていた。面接で「なぜ DB を使わなかったのか」と問われたとき、その答えは記録と食い違っていたはずである。
  - **言い換えではなく、リストから削除した。** あのリストは開発者が起点となったものだけを保持するために存在する。表現を和らげて残せば、他者に属する功績を静かに保持することになる。削除の事実を注記として明示したのは、無言の削除は単なる整理と区別がつかないからである。
  - **GSD Pi の節を、AI の記憶による要約から書いてはいない。** 開発者から「GSD のバージョンと GitHub リポジトリ名を見てほしい」と指示があったため、事実を調べた上で記述した — `@opengsd/gsd-pi`、インストール済みかつ npm 上の最新も v1.11.0、リポジトリは `open-gsd/gsd-pi`、アーカイブされていない。提出物のドキュメントにおいて記憶からバージョンを書くことは、ログの規則が防ごうとしている「検証できないように見える主張」の典型である。
  - **自動化の節は「未実装」と明記した。** Jira / Notion 連携も CodeRabbit 型のレビュー・ループも構想であって機能ではない。README の他の部分と同じ語り口で書けば、レビュアーがこれから見るものを誤って伝えることになる。両言語とも、節の冒頭で未実装であることを述べている。
  - **自動化の節でマージの境界を再確認した。** 自動化が及ぶのは修正の*提案*までであり、「エージェントは決してマージしない」は影響を受けない。この一文がなければ、PR の修正を自動化する節は、本リポジトリがもっとも明示している規則を緩める意図の表明として読まれてしまう。
- **人間が決めたこと:**
  - **訂正そのもの** — MongoDB の帰属が自分の役割を過大に書いていると気づき、それを申告したこと。
  - **GSD Pi を使った理由**（本人の選択による）：コードより先に計画を文書化させること、課題が要求する監査証跡が副産物として残ること、AI の作業をレビュー可能な大きさに保てること、セッションをまたいでも一貫すること。
  - **今回 Superpowers / TDD を採らなかった理由:** *「いま必要なのは一貫性であって、TDD という手法ではない」*。方法論上の主張として飾らず、本人の言葉のまま記録した。
  - 自動化と Superpowers の節を書くこと自体の依頼。
- **レビュー:** `npm run lint` クリーン、`npm run typecheck` クリーン、`npm test` 243 件成功 — ドキュメントの変更であっても Node 24.18.1 上で実行した。規則は「実行すること」であって「不要かどうかを自分で判断すること」ではないためである。節の対応は見出し数で確認した（各言語に新規 `###` 3 節）。GSD Pi に関する事実は記憶からではなく、npm レジストリと GitHub API に対して確認した。エントリ数の一致：各ファイル 12。
- **そのまま採用したか、修正したか:** MongoDB の訂正に関する開発者の記述は、一読では両義的だった — 自分が MongoDB を推したとも、単に外すことを承認しただけとも読めた。物語として据わりのよい方を選ばず、AI は問い返し、開発者が確認した：*AI が外すことを提案し、人間が承認した*。現在記録されているのはこれである。「捏造せず確認する」という規則が本ファイルの帰属の誤りを捕まえたのはこれで 2 度目であり、それはログに対する反証ではなく、規則の有効性の論拠である。
